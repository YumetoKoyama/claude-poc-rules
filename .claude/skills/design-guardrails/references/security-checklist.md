# セキュリティ設計チェックリスト（security-checklist）

`セキュリティ設計.md`（認証・認可の正典）に、以下の項目が「方針」ではなく **確定値** で記述されているかを確認する。`design-from-requirements` の手順 9.2 と `review-design` の `security-design` 観点から参照する（RC-05）。

---

## 1. 認証（JWT ライフサイクル）

- [ ] JWT 失効方針が確定している（STATELESS なら「logout はクライアント側トークン破棄」と明記。失効が要るならブラックリスト設計を記述）
- [ ] アクセストークン／リフレッシュトークンの有効期限が **値** で記述されている
- [ ] リフレッシュの有無と方式が確定している
- [ ] 署名アルゴリズム・鍵管理方針が記述されている

## 2. パスワード／認証情報

- [ ] パスワードハッシュ方式と **BCrypt コスト（12 以上）** が確定値で記述されている
- [ ] パスワードポリシー（要件 `非機能要件.md` から継承）が反映されている
- [ ] パスワードリセットの **レート制限** が記述されている
- [ ] パスワードリセット等の **メール送信はトランザクション外** で実行する設計になっている

## 3. ログイン試行制御

- [ ] ログイン試行ロックの **保存先が 1 つに確定**（DB か Redis）している（二元化していない）
- [ ] ロック条件（試行回数・ロック時間）が値で記述されている
- [ ] ユーザー列挙防止（存在しないメールでも同一応答、400 はメール形式エラーのみ）が記述されている

## 4. 認可・テナント分離

- [ ] 全 operationId × 必要ロール × テナント条件が `認可設計.md`／`セキュリティ設計.md` に網羅されている（public は public と明記）
- [ ] `@PreAuthorize` 規約（認可は @PreAuthorize に集約、UseCase 内の手書きロールチェックと二重管理しない）が記述されている
- [ ] 行レベル認可（自テナント／自リソースのみ操作可）の実装方式が記述されている
- [ ] テナントフィルタが SELECT だけでなく **UPDATE / DELETE / COUNT / 集計** にも適用される設計になっている
- [ ] **テナント越境は 404、自テナント内の権限不足は 403** に応答コードが統一されている

## 5. 通信・CORS

- [ ] CORS 許可オリジンが **値** で記述されている（ワイルドカード乱用が無い）
- [ ] 通信暗号化（HTTPS 前提）が記述されている
- [ ] CSRF 対策（Cookie 認証を採る場合）が記述されている

## 6. 時刻・監査

- [ ] 時刻取得は **Clock 経由**（テスト可能・固定可能）とする設計になっている
- [ ] 監査ログ出力箇所（`運用設計.md` と整合）が記述されている
- [ ] 機微情報（パスワード・トークン）をレスポンス・ログに出さない方針が記述されている

## 7. 外部 IF の実配線

- [ ] メールアダプタ（EXT-001 等）の実配線方針が記述され、スタブ放置を Issue 完了条件で防ぐ旨が示されている

---

> いずれかが「方針止まり」（例:「適切に設定する」「高いセキュリティを確保する」）の場合は `security-design` の指摘対象。確定値が要件で未確定の場合は `概要.md` の未解決事項へ切り出し ESCALATE する（設計フェーズで要件の意思決定をしない）。
