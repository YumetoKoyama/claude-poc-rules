# 設計アンチパターン詳細（negative-patterns）

設計フェーズで再発しやすいアンチパターンと、正しい設計（置き換え先）を対にして示す。`review-design` はこれを観点の根拠に用い、`design-from-requirements` / `fix-design` は出力前にこれと突合する。

---

## A. アーキテクチャ／レイヤ責務の崩れ

### A-1. Controller 肥大化

- ❌ アンチパターン: Controller の operation 説明（OpenAPI `description`）や方式設計に「Controller で在庫を確認し、足りなければ別テーブルを更新し、通知を送る」のように **業務判定・複数集約整合・トランザクション境界・通知発火** を Controller に集約する前提を書く。
- ✅ 正しい設計: Controller は「リクエスト受領→DTO 変換→UseCase 呼び出し→レスポンス整形」に限定する。業務判定・トランザクション境界・複数集約整合は UseCase（application 層）に置く。設計書（`方式設計.md`・各 operation の `description`）では責務分担を明記する。
- 関連: B-09〜B-11, B-20〜B-23（RC-04）。

### A-2. 認可を FE に寄せる

- ❌ アンチパターン: 「管理者だけがこのボタンを押せる（FE で非表示にする）」だけを設計し、API 側の `@PreAuthorize` 相当・テナントフィルタ・行レベル認可を設計しない。自他判定（own/other）を FE の表示制御に委ねる。
- ✅ 正しい設計: 防御の正典は **API 側**。`認可設計.md` に全 operationId × 必要ロール × テナント条件を定義し、行レベル制御（自テナント/自リソースのみ）を Service 層のクエリ条件として設計する。FE の非表示/非活性は UX 補助に過ぎず、設計上の防御点ではないと明記する。
- 関連: S-01, S-21, M-04〜M-06（RC-03）。

### A-3. application 層の依存逸脱

- ❌ アンチパターン: UseCase が `org.springframework.security.*` / presentation の DTO / `NotificationRepository.save` を直接呼ぶ前提の設計。
- ✅ 正しい設計: 認証主体は引数（認証済みユーザー ID 等）で受け取り、通知は `ApplicationEventPublisher` ＋ EventListener 経由とする。presentation DTO は Controller でのみ扱う。
- 関連: B-09, B-10, B-26（RC-04）。

## B. 並行性・整合性制御の欠落（RC-01）

### B-1. read-modify-write での先着・上限保証

- ❌ アンチパターン: 「応募数を SELECT して上限未満なら INSERT」「ステータスを SELECT して受付中なら UPDATE」をアプリ層だけで行う設計（同時実行で二重成約・上限超過が起きる）。
- ✅ 正しい設計: 先着・上限・二重不可は **DB 一意制約／条件付き UPDATE（`UPDATE ... WHERE status='OPEN'` の更新件数判定）／行ロック（`SELECT ... FOR UPDATE`）** で保証する。`tables/*.md` に version 列の要否と一意制約を明記し、`sequences/*.md` にロック取得順序（どのテーブルをいつ `FOR UPDATE` で掴むか、セット連動の巻き込みロック含む）を図示する。
- 関連: B-01〜B-08, S-08〜S-14, R-03。

### B-2. 非正規化カウンタ単独での上限判定

- ❌ アンチパターン: `applications_count` カラムを増やして上限チェックの唯一の根拠にする。
- ✅ 正しい設計: カウンタは表示用の非正規化に留め、上限の真の保証は一意制約／条件付き UPDATE／実レコード COUNT に置く。

### B-3. ロック順序未設計のデッドロック

- ❌ アンチパターン: 複数テーブルを更新するフローでロック取得順序を決めない。
- ✅ 正しい設計: 全フローで同一のロック取得順序（例: 親→子、ID 昇順）をシーケンスに描き、`共通部品設計.md` にデッドロック防止方針を記載する。

### B-4. テーブル定義の不完全（暗黙の欠落）

- ❌ アンチパターン: `tables/*.md` に PK・桁・nullable・一意制約・FK 参照先カラム型・インデックス方針のいずれかを書かず、実装者の判断に委ねる。
- ✅ 正しい設計: 上記すべてを明記し、不要な項目は「なし」と明示する。設計だけで物理スキーマが一意に決まる状態にする。

### B-5. tables ↔ api の型・桁の不整合

- ❌ アンチパターン: DB `VARCHAR(50)` なのに API `maxLength` 未指定 or 255、DB `BIGINT` を API で `string`、enum 値集合が DB と API で食い違う。
- ✅ 正しい設計: 型・桁・必須・enum 値域を `tables/*.md` と `api/*.yaml` で一致させる（`コード値定義.md` → `_common.yaml` → tables の enum 三点一致を含む）。

### B-6. 一意制約の単位ずれ

- ❌ アンチパターン: 「同一ユーザーの二重応募不可」なのに UNIQUE を `(user_id)` 単独や無関係なカラムに付ける／そもそも付けない。
- ✅ 正しい設計: 業務の重複単位（例: `(user_id, event_id)`）に一致した UNIQUE を `tables/*.md` に定義し、`concurrency` 観点と突合する。

## C. 界面契約の分散・二重管理（RC-02 / RC-06）

### C-1. ErrorResponse の分散

- ❌ アンチパターン: ErrorResponse / エラーコード体系を `_common.yaml` と `共通部品設計.md` の両方で定義する、各 API YAML に ErrorResponse を個別定義する。
- ✅ 正しい設計: ErrorResponse・エラーコード enum は `_common.yaml` の `components/schemas/ErrorResponse` に **一元定義** し、各 YAML は `$ref` のみ。`共通部品設計.md` は **実装方式（例外ハンドラのマッピングロジック・例外クラス→HTTP ステータス対応）のみ** を書き、コード体系を再定義しない。
- 関連: S-02〜S-07, S-18〜S-20, F-04, F-18, RV-01。

### C-2. スキーマ名の重複

- ❌ アンチパターン: 複数 YAML で同名 `MessageResponse` を別定義する。
- ✅ 正しい設計: 共通スキーマは `_common.yaml` に集約し名前を一意にする。

### C-3. JSON 実フィールド名の食い違い

- ❌ アンチパターン: BE DTO が `errorCode`、FE が `code` を読む等、JSON 上の実名が文書間で食い違う設計。
- ✅ 正しい設計: `_common.yaml` のプロパティ名（`code` / `message` / `details[].field` / `details[].reason` 等）を一字一句の正典とし、実装はそれに一致させる。

## D. データ需給の断絶（2026-06-12 の核心）

### D-1. 供給元の無い表示項目

- ❌ アンチパターン: 画面 md の「出力・表示内容」に項目を並べるが、その値を返す API（operationId.フィールド）が存在しない／画面 md に取得経路が書かれていない。
- ✅ 正しい設計: 画面 md の表示項目表に **データ源列（operationId.フィールド）** を必須化する。供給元が無い項目を見つけたら、その場で API 設計（レスポンス追加または `/me`・`LoginResponse` 等の新設）に反映する。

### D-2. ログイン直後／共通ヘッダーのデータ源欠落

- ❌ アンチパターン: ヘッダーに表示するユーザー名・テナント名・ロールが、ログインシーケンスや `/me` から取得できる設計になっていない。
- ✅ 正しい設計: ログインシーケンス（`sequences/*.md`）で「ログイン後に共通レイアウトへ表示するデータの取得経路」を `LoginResponse` または `/me` 相当として明示する。

### D-3. パラメータ出所の不明

- ❌ アンチパターン: API のパス変数・クエリパラメータの値が、前画面のどの項目・どのレスポンスフィールドから来るか不明。
- ✅ 正しい設計: 画面遷移・シーケンスでパラメータの出所を辿れるようにする。

## E. 性能・認可網羅の欠落（RC-03 / RC-11）

### E-1. 全件取得・N+1

- ❌ アンチパターン: 一覧 API をページング無しで全件返す設計、関連を 1 件ずつ取得する設計。
- ✅ 正しい設計: 一覧は DB ページング（`PageParam`/`SizeParam`）を前提にし、関連取得は JOIN / バッチフェッチを設計に明記する。

### E-2. 認可網羅の欠落

- ❌ アンチパターン: 一部 operationId が `認可設計.md` に行を持たない。`isAuthenticated()` のみで、本来ロール限定が必要なエンドポイント（合意・ユーザー追加等）を素通りさせる。
- ✅ 正しい設計: 全 operationId が認可設計に行を持つ（public は public と明記）。テナント越境は 404、自テナント内の権限不足は 403 に統一する。

### E-3. 必須/任意・enum の不整合

- ❌ アンチパターン: 要件で「必須」の項目が DB で nullable、API で optional になる（またはその逆）。enum 値が要件・DB・API で食い違う。
- ✅ 正しい設計: 要件の必須 → DB NOT NULL → API required を一致させる。enum は `コード値定義.md` → `_common.yaml` で値・表示名を一致させる。
