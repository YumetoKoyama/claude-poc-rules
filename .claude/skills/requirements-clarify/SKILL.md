# 要件定義書の曖昧さ解消（requirements-clarify）

> **パス解決（マルチリポジトリ対応）**: `docs/requirements/` は docs リポジトリ（claude-poc-docs）ルート相対のパス。
> 親アンブレラから実行している場合は `claude-poc-docs/` を前置する。

対象: $ARGUMENTS（省略時は `docs/requirements/functional/` 配下の全ファイル）

## 役割

`requirements-from-input` が生成した要件定義書に残る曖昧・未決領域を走査し、実装・テスト設計に影響する項目を最大 5 問、1 問ずつ対話形式で確認する。得られた回答を対象ファイルに書き戻し、`オープン課題.md` を更新する。

**このスキルは `requirements-loop`（自動反復）の前に任意で呼ぶ対話ステップ**。要件定義書が存在しない場合は `requirements-from-input` を先に実行すること。

---

## 手順

### Step 1: 入力の読み込み

1. 引数で指定されたパス、または `docs/requirements/functional/*.md` を全件 Read する。
2. `docs/requirements/業務ルール.md` `docs/requirements/データモデル.md` `docs/requirements/非機能要件.md` `docs/requirements/オープン課題.md` も Read する。
3. 読み込んだファイル一覧を内部に保持する（以降の step で参照）。

---

### Step 2: 9 カテゴリ曖昧さ走査

以下の 9 カテゴリを順に走査し、各カテゴリの状態を **Clear / Partial / Missing** で記録する（内部メモ、出力しない）。

| # | カテゴリ | 走査観点 |
|---|---------|---------|
| 1 | **機能スコープ・境界** | スコープ外の明示・複数ロールの使い分けが曖昧・P1 ストーリーだけで MVP が成立するか |
| 2 | **データモデル・エンティティ** | 主要エンティティの識別子一意性・状態遷移の欠落・スナップショット要否・データ規模感 |
| 3 | **UX フロー・インタラクション** | 空状態/ローディング/エラー状態の振る舞い・操作完了後の遷移先・アクセシビリティ制約 |
| 4 | **非機能品質属性** | 応答時間目標・同時接続数・可用性目標・セキュリティ制約（パスワードポリシー等）の未確定 |
| 5 | **外部依存・連携** | 外部 IF の失敗時挙動・認証方式・プロトコルバージョン・リトライ方針 |
| 6 | **エッジケース・例外処理** | 同時操作の競合・取消/差し戻し要否・削除中（論理削除〜物理削除間）データの表示 |
| 7 | **制約・トレードオフ** | 技術制約・第 1 版で対象外とした機能の根拠・切り捨てた代替案の明示 |
| 8 | **用語・表記の整合** | 同一概念に複数の表記（例: ユーザ／ユーザー）・用語集未登録の業務用語・`[要確認]` マーカーの残留 |
| 9 | **完了シグナル** | AC の検証可能性（Given/When/Then 形式）・SC-XXX に定量指標があるか・エッジケース AC-401 の有無 |

**質問候補キューの生成（内部、最大 5 件）**:
- Partial / Missing のカテゴリのうち、実装・テスト設計・スコープ決定に影響度が高い順に最大 5 件を選ぶ
- 優先順位: スコープ決定 > セキュリティ/データモデル > UX フロー > 非機能 > 用語整合
- 同じカテゴリから 2 件以上選ぶより、カテゴリを分散させる
- すでに `オープン課題.md` に Q-ID が切り出されている項目は質問候補から除外する

---

### Step 3: 対話ループ（1 問ずつ、最大 5 問）

候補キューから 1 問ずつ提示する。**次の質問は前の回答が確定するまで表示しない**。

#### 選択肢付き質問の提示形式

```
## 質問 [N/最大5]: [カテゴリ名]

**背景**:
[該当する要件定義の引用・文脈（1〜3 行）]

**確認事項**:
[具体的な質問]

**推奨**: 選択肢 [X] — [推奨理由（1〜2 文）]

| 選択肢 | 内容 | 影響 |
|--------|------|------|
| A | [選択肢 A の説明] | [選択した場合の影響] |
| B | [選択肢 B の説明] | [選択した場合の影響] |
| C | [選択肢 C の説明（必要に応じて）] | [影響] |
| 独自回答 | 独自の短い回答（5 語以内） | — |

「A」「B」のように選択肢記号で答えるか、推奨に同意する場合は「推奨」と答えてください。
```

#### 短答形式（離散選択肢が成立しない場合）

```
## 質問 [N/最大5]: [カテゴリ名]

**背景**: [文脈]

**確認事項**: [質問]

**提案**: [推奨する答え] — [理由（1〜2 文）]

5 語以内の短い回答で答えてください。提案でよければ「提案」と答えてください。
```

#### 回答処理ルール

- 「推奨」「提案」「yes」→ 提示した推奨/提案をそのまま採用
- 「A」「B」「C」→ 対応する選択肢を採用
- 独自テキスト → そのまま記録
- 「終了」「スキップ」「次へ」→ 残りキューをすべてスキップして Step 4 へ
- 回答が曖昧な場合は同じ質問番号で再確認（質問消費カウントに含まない）

---

### Step 4: 回答の書き戻し

各回答について、影響するセクションを判断して書き戻す。

| 回答の種類 | 書き戻し先 |
|-----------|-----------|
| 機能スコープ・ロール分岐 | `functional/[機能名].md` の「前提条件」または「ユーザーストーリー」 |
| AC の追加・更新 | `functional/[機能名].md` の「受け入れ条件」（Given/When/Then 形式） |
| 成功基準（SC-XXX）の定量化 | `functional/[機能名].md` の「成功基準」 |
| エンティティ・状態遷移 | `データモデル.md` |
| 非機能要求値の確定 | `非機能要件.md` の該当項目 |
| 用語統一 | `用語集.md` に追加 + 本文中の表記を統一 |
| 外部 IF の補足 | `外部インターフェース一覧.md` |
| 業務ルールの明確化 | `業務ルール.md` |

**書き戻しルール**:
- 既存のセクションを破壊しない（加算型で追記または最小限の置換）
- `[要確認]` マーカーが回答で解消された場合はマーカーごと削除し、確定した記述に置き換える
- 矛盾する旧記述が残る場合は削除して置き換える（重複・矛盾 NG）
- ファイルごとに 1 回の Write/Edit にまとめる

**`オープン課題.md` の更新**:
- 回答で解消された Q-ID は「状態」を `closed`、「決定内容」に回答内容、「closed 日」に今日の日付を記入する
- 新たに判明した未解決事項があれば新規行として追加する

---

### Step 5: 完了レポート

以下の形式で出力する。

```
## requirements-clarify 完了レポート

- 質問数: N 問（最大 5）
- 更新ファイル: [ファイル一覧]
- クローズした Q-ID: [Q-ID 一覧]

### カテゴリ別カバレッジ

| カテゴリ | 状態 |
|---------|------|
| 機能スコープ・境界 | Clear / Partial（要 review 指摘） / Deferred |
| データモデル・エンティティ | ... |
| ...（9 カテゴリ分） | ... |

### 次のステップ

- [ ] `/requirements-loop` で自動レビューを実行する
  （または問題が軽微なら直接 `/review-requirements` から開始可）
```

---

## 注意事項

- このスキルは **対話ステップ**であり、`requirements-loop` の自動反復ループには組み込まれない
- 最大 5 問の制限を必ず守る（同一質問の再確認は 0.5 問扱い、カウントしない）
- 「設計フェーズで決めるべき内容」（フレームワーク選定・API パス・テーブル設計）は質問しない
- `オープン課題.md` の Q-NF\* や Q-DM\* が多く残っている場合は、質問で解消してから `requirements-loop` を呼ぶよう促す

## 完了条件

- [ ] 9 カテゴリ走査が完了し、カバレッジが記録されている
- [ ] 最大 5 問の回答が対象ファイルに書き戻されている
- [ ] `オープン課題.md` が更新されている（解消済み Q-ID のクローズ）
- [ ] 完了レポートが出力されている
