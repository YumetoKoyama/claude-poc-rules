# 設計着手前リサーチ（design-pre-research / Phase 0 Research）

> **パス解決（マルチリポジトリ対応）**: `docs/requirements/` は docs リポジトリ（claude-poc-docs）ルート相対のパス。
> 親アンブレラから実行している場合は `claude-poc-docs/` を前置する。

入力: $ARGUMENTS（省略時は `docs/requirements/` 全件）

## 役割

`design-loop` を起動する前に `docs/requirements/オープン課題.md` の「**設計着手前クローズ必須**」区分に該当する未解決 Q-ID を洗い出し、業界標準・プロジェクト文脈・非機能要件テンプレートをもとに解決案を合成してユーザーに確認する。  
承認された決定内容を対象ファイルへ書き戻し、Q-ID をクローズすることで、`design-loop` が未確定事項を抱えたまま設計に進む事態を防ぐ。

**このスキルは `design-loop` の前に任意で呼ぶ**。`オープン課題.md` に未解決の必須クローズ Q-ID が 0 件なら即完了を報告する。

---

## 手順

### Step 1: 入力の読み込み

以下を Read する:

1. `docs/requirements/オープン課題.md` — Q-ID 一覧・状態・クローズ運用ルールを把握
2. `docs/requirements/非機能要件.md`
3. `docs/requirements/データモデル.md`
4. `docs/requirements/外部インターフェース一覧.md`
5. `docs/requirements/移行要件.md`
6. `docs/requirements/概要.md` — プロジェクトの業種・規模感・スコープを把握
7. `docs/requirements/業務ルール.md`
8. `docs/requirements/functional/*.md` — 機能の文脈を把握

---

### Step 2: 設計着手前クローズ必須 Q-ID の抽出

`オープン課題.md` の課題一覧から、以下の区分に該当しかつ `state == open` の Q-ID をすべて抽出する。

| 区分 | Q-ID プレフィックス例 | 対応ファイル |
|------|---------------------|------------|
| パスワードポリシー・セッション・通信暗号化 | `Q-NF*`（セキュリティ系） | `非機能要件.md` |
| 対象ブラウザ・対象デバイス | `Q-NF*`（クライアント環境系） | `非機能要件.md` |
| バックアップ・障害検知・稼働時間 | `Q-NF*`（運用系） | `非機能要件.md` |
| 主要エンティティ・状態定義・スナップショット方針 | `Q-DM*` | `データモデル.md` |
| メール送信・バッチ・外部連携 | `Q-EI*` | `外部インターフェース一覧.md` |
| 初期データ・マスタデータ・移行範囲 | `Q-MIG*` | `移行要件.md` |
| 主要業務ルール（金額単位・物品種別・状態遷移境界条件等） | 区分依存 | `業務ルール.md` / `functional/*.md` |

抽出した Q-ID がゼロ件なら以下を出力して**完了**:

```
✅ design-pre-research: 設計着手前クローズ必須の未解決 Q-ID はゼロ件です。
   /design-loop を起動できます。
```

---

### Step 3: Q-ID ごとに解決案を合成

抽出した Q-ID ごとに、以下の情報源から解決案を合成する:

**情報源の優先順位**:
1. `docs/requirements/` 内の他ファイル（同プロジェクトの文脈・業務ルール）
2. `docs/architecture/constitution.md`（存在する場合、プロジェクト設計原則）
3. 業界標準・ベストプラクティス（OWASP / Web アプリ一般慣習 / 類似ドメインの標準値）

**解決案の質基準**:
- 定量値を示す（「高い」ではなく「8 文字以上、英数字記号混在必須」）
- 根拠を 1 〜 2 文で明示する
- 第 1 版スコープとして現実的か（過剰スペックを避ける）
- 複数の選択肢がある場合は最大 3 案を列挙し推奨案に ★ を付ける

---

### Step 4: 解決案のユーザー確認（バッチ提示）

Q-ID 数に応じて確認単位を調整する:
- 5 件以下: 全件まとめて提示 → 一括確認
- 6 件以上: カテゴリ別にグループ化して提示 → グループ単位で確認

**提示形式**:

```
## Phase 0 Research — 設計着手前クローズ必須 Q-ID の解決案

以下の Q-ID について解決案を合成しました。
各案を確認して「承認」または修正内容をお知らせください。

---

### [Q-NF1] パスワードポリシー未確定

**背景**: 非機能要件.md のセキュリティセクションが TBD のまま残っています。

**解決案**:

| # | 案 | 決定内容 | 根拠 |
|---|----|---------|------|
| ★ A | 標準ポリシー | 8 文字以上・英大小文字＋数字混在必須・記号任意。連続失敗 5 回でアカウントロック（30 分自動解除） | OWASP Authentication Cheat Sheet の推奨ベースライン。Web アプリ第 1 版として適切 |
| B | 厳格ポリシー | 12 文字以上・英大小文字＋数字＋記号すべて必須。失敗 3 回ロック（管理者解除のみ） | 金融・医療系で採用される厳格基準。利便性コストが高い |
| C | 独自回答 | ユーザー指定 | — |

「A」「B」または具体的なポリシーを入力してください（推奨: A）。

---

### [Q-NF2] 対象ブラウザ未確定

... （同様の形式）
```

**回答処理ルール**:
- 「承認」「推奨」「A」「B」「C」→ 対応する案を採用
- 独自テキスト → そのまま採用（整合性確認後に書き戻す）
- 「スキップ」→ その Q-ID は今回未解決のまま残す（後述の未解決リストへ）
- 「終了」→ 以降の Q-ID をすべてスキップして Step 5 へ

---

### Step 5: 承認済み解決案の書き戻し

各 Q-ID の承認済み決定内容を、対応する要件定義ファイルへ書き戻す。

**書き戻しルール**:

| Q-ID 区分 | 書き戻し先 | 書き戻し方法 |
|-----------|-----------|-------------|
| `Q-NF*`（セキュリティ系） | `非機能要件.md` のセキュリティセクション | TBD をそのまま確定値に置換。参照リンク（`> オープン課題 Q-NF1 クローズ済み`）を削除 |
| `Q-NF*`（ブラウザ/デバイス） | `非機能要件.md` のアクセシビリティ・ブラウザセクション | 同上 |
| `Q-NF*`（運用系） | `非機能要件.md` の運用・障害対応セクション | 同上 |
| `Q-DM*` | `データモデル.md` の該当エンティティ / 状態遷移 | 未記述の列 / ステータスを追記 |
| `Q-EI*` | `外部インターフェース一覧.md` の該当 EXT-XXX | 失敗時挙動 / 冪等性 等を追記 |
| `Q-MIG*` | `移行要件.md` の該当 MIG-XXX | 移行範囲・件数規模・完了判定基準を追記 |
| 業務ルール系 | `業務ルール.md` または `functional/[機能名].md` | 断定値として追記 |

**`オープン課題.md` の更新**（書き戻し後に実施）:
- 承認済み Q-ID の行: `状態` を `closed`、`決定内容` に承認した案の要約、`closed 日` に今日の日付を記入
- スキップした Q-ID: 状態は `open` のまま変更しない

**書き戻し後の整合チェック**:
- `非機能要件.md` に TBD / `Q-NF*` 参照が残っていないか
- `データモデル.md` の状態遷移（ST-XXX）に未記述がないか
- 書き戻した値が他のファイル（`業務ルール.md`・`functional/*.md`）と矛盾しないか
矛盾を検出した場合は修正前に警告として提示し、ユーザーに対応を確認する。

---

### Step 6: 完了レポートの出力

```
## design-pre-research 完了レポート

### クローズした Q-ID（[N] 件）

| Q-ID | カテゴリ | 決定内容（要約） | 書き戻し先 |
|------|---------|----------------|-----------|
| Q-NF1 | パスワードポリシー | 8 文字以上・英数字混在・失敗 5 回ロック | 非機能要件.md |
| ...  | ...     | ...            | ...       |

### 未解決のまま残った Q-ID（[M] 件）

| Q-ID | カテゴリ | 未解決の理由 |
|------|---------|------------|
| Q-NF3 | 稼働時間帯 | スキップ（業務側に確認が必要） |

> ⚠️ 未解決 Q-ID が残っています。`/design-loop` を起動する前に人間が確認・クローズしてください。
> 設計着手前クローズ必須の区分に該当するため、このまま `/design-loop` を起動すると
> スタック確定ゲートまたは `review-design` の BLOCK 対象になります。

### 次のステップ

- 未解決 Q-ID が 0 件: `/design-loop` を起動できます
- 未解決 Q-ID が残る場合: 人間が確認してクローズ後に `/design-loop` を起動してください
```

---

## 注意事項

- このスキルは **設計判断を強制しない**。ユーザーが「スキップ」した Q-ID は人間の判断に委ねる
- 解決案の合成に外部 Web 検索は使用しない（プロジェクト文脈と業界標準から合成する）
- 書き戻しは **加算型**（既存セクションの破壊禁止）。TBD マーカー / 参照リンクのみ置換する
- `業務ルール.md` の主要業務ルール系 Q-ID（金額単位・競合解消ルール等）は業務知識が必要なため、原則ユーザー入力を要求する（推奨案は提示するが強制しない）

## 完了条件

- [ ] 設計着手前クローズ必須 Q-ID の全件抽出が完了している
- [ ] 各 Q-ID に解決案が合成され、ユーザーが確認・承認または明示スキップしている
- [ ] 承認済み Q-ID の決定内容が対応ファイルに書き戻されている
- [ ] `オープン課題.md` の承認済み Q-ID が `closed` に更新されている
- [ ] 完了レポート（クローズ件数・残存未解決件数）が出力されている
