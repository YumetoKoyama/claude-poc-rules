# 設計変更に伴う Issue 再オープン/追加起票

> **位置づけ**: 変更管理工程の終段。`design-amendment` で設計を直したあと、その変更の影響を受ける既存 Issue を再オープン（クローズ済みなら）・更新（オープン中なら追記）し、設計変更で新たに必要になった作業は追加 Issue として起票する。`create-issues-from-design`（初回の一括起票）の差分版にあたる。
>
> **採択ゲートと起動トリガの踏襲（必須）**: 設計変更が docs の `main` にマージ済み（＝採択済み）であることを前提に起票する。**実装の開始は人間が対象 Issue に `@claude` とコメントすること**であり、本スキル・Claude が自ら `@claude` コメントや PR マージをして実装を起動してはならない。Issue 本文の `@` トークンは必ずバッククォートで囲み、無関係なメンション通知を防ぐ（`@claude` は本文に書かない）。

> **パス解決（マルチリポジトリ対応）**: 本スキル内の `docs/requirements/`・`docs/design/`・`docs/test/` は **docs リポジトリ（claude-poc-docs）ルート相対**のパスを指す。
> - docs リポジトリをカレントとして実行している場合: そのまま使う。
> - 親アンブレラ（claude-poc-rules）から実行している場合（カレント直下に `claude-poc-docs/` が存在する場合）: これらすべてのパスに `claude-poc-docs/` を前置して読み書きする。
> - 起票先は対象の実装リポジトリ（backend / frontend / batch）。影響分析で推定したリポを対象にする。

入力: $ARGUMENTS

## 前提条件

- 設計変更（`design-amendment`）が実施され、`docs/design/変更履歴.md` に変更エントリが追記されていること。
- 変更が docs の `main` にマージ済み（採択済み）であること。未マージなら起票せず中断し、人手レビュー・マージを依頼する（`git log origin/main -- docs/design/変更履歴.md` 等で確認）。
- `gh` CLI がインストール・認証済みであること（`gh auth status` で確認）。
- 対象リポジトリに `.github/ISSUE_TEMPLATE/`（screen / api / interface / table / bug）と必要なラベルが用意されていること。

## 成果物

- 再オープン/更新した既存 Issue と、新規起票した追加 Issue の一覧（番号・タイトル・URL・アクション区分・付与ラベル）の Markdown テーブル
- RTM（`docs/test/トレーサビリティマトリクス.md`）の Issue# 列の更新（追加 Issue を反映）

## 手順

### 1. 入力の読み込みと採択確認

1. 影響分析ファイル（`impact-analysis-from-change` の出力）の「再オープン/追加起票の候補 Issue」セクションと、`docs/design/変更履歴.md` の対象エントリを Read する。
2. 設計変更が docs の `main` にマージ済みであることを確認する。未マージなら中断して人手マージを依頼する。
3. 候補 Issue 群と、変更で新たに必要になった作業（新画面・新 API・新テーブル等）を整理する。

### 2. 既存 Issue の特定と状態確認

1. 候補 Issue 番号それぞれについて `gh issue view <番号> --json number,title,state,labels` で現在の状態（OPEN / CLOSED）を取得する。
2. 影響分析の波及理由と突合し、本当に再着手が必要な Issue かを判定する（影響範囲外を巻き込まない）。

### 3. アクションの決定と実行

各影響 Issue について、状態に応じて次のいずれかを行う。

- **クローズ済み × 再実装が必要** → `gh issue reopen <番号>` で再オープンし、変更内容コメントを追記（下記テンプレ）。
- **オープン中 × 仕様が変わる** → 既存 Issue にコメントで変更内容を追記（再オープンは不要）。
- **既存 Issue で表現できない新規作業** → `create-issues-from-design` と同じ粒度・ラベル・テンプレートで **追加 Issue** を起票する（画面=type:screen / API=type:api / IF=type:interface / テーブル=type:table）。
- **影響なしと判定** → 何もしない（その旨を一覧に「不要」と記録）。

再オープン/コメント時の本文テンプレ（`@` はバッククォートで囲む）:

```markdown
## 設計変更による再着手

- 変更履歴: `docs/design/変更履歴.md`（<対象エントリ>）
- 変更理由区分: <ESCALATE / 要件変更 / レビュー指摘>
- 影響分析: `docs/design/影響分析/impact-<...>.md`
- 変更点サマリ: <この Issue に関係する変更の要点>
- 再着手の範囲: <この Issue で直すべき層・ファイル候補>

実装の開始は、人間が本 Issue に `@claude` とコメントした時点とする（本コメントでは起動しない）。
```

### 4. 依存順序の明示

追加 Issue・再オープン Issue 間に実装依存（DB → BE API → FE 画面）がある場合は、本文に `Depends on: #<番号>` を明記し、依存元が未完了のまま下流を着手しないようにする。

### 5. RTM の更新

`docs/test/トレーサビリティマトリクス.md` の該当行の Issue# 列を、再オープン/追加した Issue 番号で更新する（横串カバレッジの正典を最新化）。

### 6. まとめ出力

再オープン/更新/追加/不要の区分付きで、Issue 番号・タイトル・URL・ラベルの一覧を Markdown テーブルで出力する。最後に「実装の開始は人間の `@claude` コメント」である旨を再掲する。

## 完了条件

- 影響を受ける既存 Issue が再オープンまたは更新され、変更内容コメントが追記されている
- 新規作業は追加 Issue として適切な粒度・ラベルで起票されている
- 依存順序（`Depends on: #XX`）が必要箇所に明記されている
- RTM の Issue# 列が更新されている
- 一覧が区分付きで出力され、`@claude` 起動トリガの注意が再掲されている

## 凡例

| 略号 | 正式名称 | 補足 |
| --- | --- | --- |
| RTM | トレーサビリティマトリクス | `docs/test/トレーサビリティマトリクス.md` |
| 変更理由区分 | ESCALATE / 要件変更 / レビュー指摘 | 変更履歴と整合させる |
| Depends on | 実装依存の明示 | DB → BE API → FE 画面 の順序事故を防ぐ |

## 注意事項

- 自ら `@claude` コメント・PR マージをして実装を起動しない（起動は人間の明示アクション）。
- Issue 本文・コメントの `@` トークンはバッククォートで囲み、無関係なメンション通知を防ぐ。
- 影響範囲外の Issue を巻き込まない（影響分析の波及理由を根拠にする）。
- 強調表記は鉤括弧 `「...」` を使う。
