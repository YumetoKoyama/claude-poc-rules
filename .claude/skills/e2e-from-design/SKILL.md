# 設計書から E2E テストを作成する

> **⚠️ 凍結中（実行禁止）**: E2E は **AWS 環境構築後に E2E リポジトリの別工程**として実施する。Playwright も未導入（セキュリティソフト対応）。本スキルが呼び出された場合は、**何も実行せず**「E2E は凍結中（AWS 環境構築後・E2E リポジトリで実施）」と報告して直ちに終了すること。

> **呼び出し元**: `/implement-from-issue` の品質ゲート（手順 5・Pattern 2 並列ファンアウト）から「E2E」担当として呼ばれる補助 skill。設計フェーズ完了後に単独起動することもできる。Agent Teams は使わない。

次の入力をもとに E2E テストを作成または更新する: $ARGUMENTS

## 指示

1. 設計ソースを読み、重要なユーザージャーニーを特定する。
   - 画面遷移: `docs/design/screens/画面遷移.md`（Mermaid）と `docs/requirements/画面一覧.md`
   - 画面別仕様: `docs/design/screens/[scr-id]-*.md`
   - API 仕様: `docs/design/api/[リソース名].yaml`（リソースごとに 1 ファイル、同リソースの全 HTTP メソッドを集約）
   - シナリオ方針: `docs/design/シナリオ戦略.md`
2. ブラウザ自動化と画面検証には Playwright MCP を使う。
3. シナリオ一覧がない場合は [e2e-scenario-template.md](e2e-scenario-template.md) を使って実行可能ケースへ落とし込む。
4. シナリオ表には関連画面 ID（SCR-XXX）を必ず含める。
5. 正常系、入力エラー、状態遷移、永続化結果をカバーする。
6. 実行は可能な限り狭い E2E スイートで行う。
7. 失敗時は、テストデータ、セレクタ、タイミング、UI 描画、バックエンド挙動、環境のどこが原因かを切り分ける。

## 失敗時の investigation フロー

1. 失敗したシナリオ、操作手順、期待結果、実結果を簡潔に整理する。
2. Playwright MCP を使って、失敗時点の画面状態、DOM、表示テキストを再確認する。
3. 仮説は 1 つに絞り、セレクタ問題、待機不足、テストデータ不整合、バックエンド不具合、React レンダリング不整合（非同期更新・状態遷移・キャッシュ）のどれかから検証する。
4. 最小再現条件で同じシナリオを再実行する。
5. 必要ならサーバーログ、HTTP 応答、DB 状態と突き合わせる。
6. 原因がテスト側かアプリ側かを明示したうえで修正する。
7. 修正後は同一シナリオと近接シナリオを再実行して回帰を確認する。

## 実行時の出力期待

- 作成または更新したシナリオ一覧（画面 ID 付き）
- Playwright MCP で確認した画面フローの要約
- 失敗時は原因候補、切り分け結果、最終原因
- 修正後に再実行したシナリオと結果
