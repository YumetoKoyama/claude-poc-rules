- 主眼: **各工程および全体で「観点・成果物として不足しているもの」を洗い出す**（例: 認可マトリクスがない、文言定義書がない 等）
- レビュアー: Claude（Cowork）

## 凡例（本レビューで導入する ID・重大度）

| 略号 | 正式名称 | 意味 |
| --- | --- | --- |
| **重要度: 高** | MUST | 一般的な Web 業務システム開発で標準的に必要な成果物／観点が欠落しており、品質・セキュリティ・追跡性に直接影響する |
| **重要度: 中** | SHOULD | あると整合性・保守性が大きく向上する。現状は他成果物に分散していて正典がない |
| **重要度: 低** | NICE | 体裁・将来拡張レベル。明示判断（「不要」宣言含む）があると親切 |
| `G-XX` | Gap・全体横断（Global） | フェーズをまたぐ不足 |
| `R-XX` | Gap・要件定義（Requirements） | 要件定義フェーズの不足 |
| `D-XX` | Gap・設計（Design） | 設計フェーズの不足 |
| `T-XX` | Gap・テスト（Test） | テストフェーズの不足 |

各指摘は「現状 / 不足している観点・成果物 / 推奨アクション（推奨成果物と配置）/ 根拠」で記す。本レビューは静的読解に基づく。

## エグゼクティブサマリ

要件定義・設計の **縦の追跡性**（UC→AC→画面→API→テーブル→テスト）と ID 体系は非常に作り込まれています。一方で、業務システムで標準的に独立成果物として持つべき **横断系の観点**が、複数の文書に断片として散在し「正典（Source of Truth）」を欠いています。とくに次の 4 点は第 1 版の品質・セキュリティに直結するため、成果物の新設を推奨します。

1. **認可（権限）マトリクス**がない。ロール × リソース × 操作の CRUD 認可が API の `@PreAuthorize` や画面仕様に分散し、一覧で検証できない（G-01）。
2. **セキュリティ設計書**がない。JWT・CORS・パスワードハッシュ・セッションが api/screens/sequences に散在し、認証認可の正典が存在しない（D-01）。
3. **メッセージ／文言定義**がない。エラー・確認・通知の表示文言が未確定（`Q-M5 暫定文言` 等）のまま画面に散らばっている（R-01）。
4. **テストの層が単体と E2E の 2 層のみ**で、結合（API/サービス間）テストと非機能テスト（性能・負荷）の工程が欠落している（T-01・T-02）。

検出: 重要度 高 6 件 / 中 7 件 / 低 4 件。以下、全体横断 → 要件 → 設計 → テストの順。

> なお、ご提示の例「外部 IF 仕様書がない」については、`docs/requirements/外部インターフェース一覧.md`（EXT-001 メール / EXT-002 バッチ）と `docs/design/IF定義.md`（エラーコード共通定義・バッチ IF 含む）でカバーされており、**外部 IF は不足ではありません**。同種の「散在しているが正典がない」観点を以下に列挙します。

## 1. 全体横断（フェーズをまたぐ観点）

### G-01【重要度: 高】認可（権限）マトリクスが成果物として存在しない

- 現状: ロール（配送依頼企業 / 運送会社、テナント管理者 / 一般ユーザー）ごとの操作可否が、API の `@PreAuthorize`、画面仕様、シーケンス図、テスト戦略の「テナント分離」に分散している。`docs/` 全体に「権限マトリクス」「認可マトリクス」「RBAC」を正典とする成果物がない（grep 0 件）。
- 不足: **ロール × リソース（ENT/画面/API）× 操作（C/R/U/D・状態遷移）の認可一覧表**。テナント越境（自社テナント外の参照・操作の 403/404）の網羅条件もここに集約すべき。
- 推奨: `docs/requirements/権限マトリクス.md`（業務観点のロール × ユースケース可否）と、`docs/design/認可設計.md`（API operationId × 必要ロール × テナント条件）を新設。`review-design` の traceability 観点に「全 operationId が認可マトリクスのいずれかの行に対応するか」を追加。
- 根拠: `docs/design/api/users.yaml` ほか `@PreAuthorize` 散在、`テスト戦略.md` の「テナント分離」項。

### G-02【重要度: 中】要件→設計→Issue→テストを一枚で追える統合トレーサビリティ・マトリクス（RTM）がない

- 現状: ペアワイズの追跡（要件→設計は `review-design` の traceability、AC→テストは `単体テストマトリクス`）は存在するが、**UC/AC を起点に「設計成果物・Issue 番号・UT/E2E テスト ID」まで一気通貫で並べた 1 表（RTM）**がない。
- 不足: カバレッジ漏れ（どの AC が設計・テストに落ちていないか）を機械的に検出する統合表。
- 推奨: `docs/test/トレーサビリティマトリクス.md`（列: UC / AC / BR / SCR / API operationId / Issue# / TC-XXX / E2E-XXX）を成果物化し、Issue 起票・実装ループで更新。
- 根拠: 追跡性は各 review skill に分散しており横串の成果物が `docs/` に無い。

### G-03【重要度: 中】セキュリティレビュー工程が 9 ステップフローに組み込まれていない

- 現状: `/security-review` コマンドは利用可能だが、`CLAUDE.md` の 9 ステップフロー（実装→PR→人手レビュー）にセキュリティレビューの関門が明示されていない。`docs/security/` は隔離・コマンド拒否ポリシー（基盤運用）であり、アプリのセキュリティ点検工程ではない。
- 不足: 実装フェーズ（PR 前）での **アプリ脆弱性レビュー観点**（認可バイパス、IDOR/テナント越境、機密情報のログ出力、JWT 検証、入力サニタイズ等）の関門。
- 推奨: `implement-loop` の品質ゲートに `/security-review` 相当の観点を 1 ステップ追加するか、`review-implementation` の security 観点を OWASP ベースで具体化。
- 根拠: `CLAUDE.md` 開発フロー、利用可能コマンド一覧の `security-review`。

## 2. 要件定義フェーズ

`requirements-from-input` / `requirements-guardrails` / `requirements-template.md` ほか。
現状の成果物群（概要・業務ルール・機能・UC 図・アクティビティ・画面一覧・データモデル・外部 IF・移行・非機能・用語集・オープン課題）は網羅性が高い。以下は標準的だが欠けている観点。

### R-01【重要度: 高】メッセージ／文言定義（メッセージ ID 体系）がない

- 現状: エラー・確認ダイアログ・通知・バリデーションの表示文言が各画面仕様に散在し、未確定のものが `Q-M5 暫定文言` のようにオープン課題化している。文言の正典がない。
- 不足: **メッセージ一覧（メッセージ ID / 区分（情報・警告・エラー・確認）/ 文言 / 表示画面 / トリガ）**。多言語化や文言レビューの単位にもなる。
- 推奨: `docs/requirements/メッセージ一覧.md`（MSG-XXX 採番）を新設し、画面仕様・API ErrorResponse・通知から MSG-XXX で参照。ID 体系に `MSG-XXX` を追加。
- 根拠: `シナリオ戦略.md` E2E-006 の「Q-M5 暫定文言」、`docs/design/IF定義.md` のエラーコード（コードはあるが利用者向け文言の正典がない）。

### R-02【重要度: 中】コード値・区分値定義（区分マスタ一覧）がない

- 現状: `JobStatus` / `BidStatus` などの列挙値は `docs/design/api/_common.yaml` に定義されているが、**業務区分値の正典が設計の API スキーマ側にしかなく**、要件側に区分一覧がない。新区分の追加・廃止の管理単位が不明確。
- 不足: **区分値定義書（区分名 / コード値 / 表示名 / 意味 / 関連 BR・状態 ST）**。
- 推奨: `docs/requirements/コード値定義.md`（概念レベル）→ 設計 `_common.yaml`（物理 enum）の対応を明記。
- 根拠: `_common.yaml` の `JobStatus` / `BidStatus`、`データモデル.md` の状態 ST。

### R-03【重要度: 中】通知・メール文面定義がない

- 現状: 通知機能・パスワードリセットメール（EXT-001）の「契機・データ」は外部 IF 一覧にあるが、**実際の本文テンプレート（件名・本文・差込項目）**の成果物がない。
- 不足: 通知タイプ別・メール別の文面テンプレート。R-01 のメッセージ一覧と統合しても可。
- 推奨: `docs/requirements/通知・文面定義.md`（通知タイプ × 文面 × 差込変数 × 関連 UC/BR）。
- 根拠: `外部インターフェース一覧.md` EXT-001、`functional/通知.md`。

### R-04【重要度: 低】帳票要件の明示判断がない／入力チェック仕様の正典がない

- 現状: 「帳票」への言及が `docs/` 全体で 0 件。移行・外部 IF は「なしの場合も明記」ルールがあるのに、帳票（PDF/CSV 出力）は要否判断自体が残っていない。また入力チェック（必須・型・桁・範囲）は画面仕様に分散し、横断の入力チェック仕様がない。
- 推奨: 非機能または外部 IF に「帳票: 第 1 版は対象外」を一行明記。入力チェックは R-01 のメッセージ一覧と紐づく `入力チェック一覧`（任意）として横串化を検討。
- 根拠: grep「帳票」0 件、「バリデーション一覧／入力チェック仕様」0 件。

## 3. 設計フェーズ

`design-from-requirements` / `design-spec-template.md` / `review-design` ほか。
画面・API（OpenAPI）・DB・シーケンスの縦の作り込みは強い。以下は横断・方式系の欠落。

### D-01【重要度: 高】セキュリティ設計書（認証・認可の正典）がない

- 現状: JWT・CORS・パスワードハッシュ・セッション・トークン有効期限が `auth.yaml` / `_common.yaml` / `SCR-001` / `ログイン認証.md` など複数に分散。`docs/design/` に認証認可を 1 枚にまとめた成果物がない。
- 不足: **セキュリティ設計書**（JWT のライフサイクル / 署名・失効 / リフレッシュ方針 / CORS 許可オリジン / パスワードハッシュ方式 / ログイン試行制御 / 認可の実装方式（`@PreAuthorize` 規約 + テナントフィルタ））。
- 推奨: `docs/design/セキュリティ設計.md` を新設し、G-01 の認可設計と統合。`CLAUDE.md` の推奨ドキュメント一式（設計）に追加。
- 根拠: grep で JWT/CORS が 30 ファイル超に散在、集約成果物なし。`tables/login_attempts.md`・`password_reset_tokens.md` の運用方針も本書で集約可能。

### D-02【重要度: 高】方式設計／システム構成図がない

- 現状: `docs/design/概要.md` は「設計サマリー（スコープ・前提・リスク・レビュー観点）」であり、**論理／物理アーキテクチャ図・コンポーネント構成・デプロイ構成（環境別）・ミドルウェア構成**を示す成果物がない。`devcontainer-setup.md` は開発環境であって本番方式ではない。
- 不足: 方式設計（フロント SPA / API / DB / バッチ / メール送信の論理構成図、環境（dev/stg/prod）と配置、認証フローのシステム間連携図）。
- 推奨: `docs/design/方式設計.md`（Mermaid のコンポーネント図 + デプロイ構成図）を新設。
- 根拠: grep「システム構成／構成図／方式設計／インフラ／デプロイ構成」を `docs/design/` 本文で 0 件。

### D-03【重要度: 中】バッチ詳細設計が IF レベル止まり／共通部品・例外設計の正典がない

- 現状: バッチは `IF定義.md`（EXT-002 等）で契機・冪等性・失敗時挙動まで記述があり良好だが、**トランザクション単位・処理単位の再実行・件数規模時の分割・監視連携といった詳細設計**がない。また共通例外ハンドラ・共通バリデーション・共通レスポンス整形といった **共通部品設計**の正典がない（ErrorResponse スキーマは `_common.yaml` にあるが実装方式の設計がない）。
- 不足: バッチ詳細設計、共通部品（横断的関心事）設計。
- 推奨: `docs/design/バッチ設計.md`、`docs/design/共通部品設計.md`（例外ハンドリング方式 / バリデーション共通化 / ロギング方式）を新設。
- 根拠: `IF定義.md` のバッチ行は IF 粒度、`テスト戦略.md` の `JobPhysicalDeleteBatch` は実装/テストに登場するが設計の詳細がない。

### D-04【重要度: 中】運用設計（監視・バックアップ・ログ運用のランブック）がない

- 現状: 非機能要件（`非機能要件.md` の運用・障害対応・データ保持・ログ監査）に「要求」はあるが、設計フェーズに**運用設計成果物**がなく、要求が設計に落ちていない（既存レビュー §3-2「非機能の要求値が設計に未突合」のテスト前段にあたる構造）。
- 不足: 監視項目・アラート閾値・バックアップ／リストア手順・ジョブ運用・ログ保持と監査ログ出力箇所の設計。
- 推奨: `docs/design/運用設計.md` を新設。`review-design` の `nonfunc-traceability` 観点（既追加済み）に「運用要求が運用設計に反映されているか」を含める。
- 根拠: `非機能要件.md` の運用章 vs `docs/design/` に運用設計ファイルなし。

## 4. テストフェーズ

`unit-test-from-design` / `e2e-from-design` / `テスト戦略.md`（=単体）/ `シナリオ戦略.md`（=E2E）。
単体と E2E の 2 層は具体的で良質。一方でテストピラミッドの中段と非機能が欠落。

### T-01【重要度: 高】結合（統合）テストの層が戦略にない

- 現状: テスト成果物は `テスト戦略.md`（単体）と `シナリオ戦略.md`（E2E）の 2 層のみ。Repository は `@DataJpaTest`+TestContainers、Controller は `@WebMvcTest`(Service モック) で、**Controller→Service→Repository→DB を実結合した API 統合テスト**や、サービス間結合（通知発火 × トランザクション境界、排他制御の実 DB 結合）が中間層として独立に計画されていない。
- 不足: 結合テスト方針・マトリクス（実 DB + 実 Service の API レベル検証）。
- 推奨: `docs/design/結合テスト戦略.md` または `テスト戦略.md` に結合層を追加し、`docs/test/結合テストマトリクス.md` を成果物化。IT-XXX の ID を採番。
- 根拠: `テスト戦略.md` の「## テスト対象範囲」は単体粒度、E2E はブラウザ。中間が空白。

### T-02【重要度: 高】非機能テスト（性能・負荷・可用性）の工程がない

- 現状: 要件で性能（一覧応答・同時ユーザー）・可用性（RTO/RPO・バックアップ）を数値確定している一方、**それを検証するテスト工程・成果物がない**。機能テストの追跡（AC↔テスト）はあるが非機能は追跡対象外。
- 不足: 性能・負荷テスト計画（目標値・シナリオ・ツール）、可用性（フェイルオーバ・リストア）確認手順。
- 推奨: `docs/test/非機能テスト計画.md`（非機能要求値 → 検証方法の対応表）。非機能要求値ごとに最低 1 検証を割り当てるルールを `CLAUDE.md` に追記。
- 根拠: `非機能要件.md` の性能・可用性章 vs テスト成果物 2 種に非機能項目なし。

### T-03【重要度: 中】セキュリティテスト・テストデータ設計・全体テスト計画がない

- 現状: 認可境界（テナント分離）は E2E/単体で扱うが、**脆弱性観点のセキュリティテスト**（IDOR、認可バイパス、JWT 改ざん、機微情報のレスポンス漏えい）が独立していない。テストデータ設計（境界値・異常系のデータセット）はファクトリ言及のみで成果物がない。テスト戦略・シナリオ戦略はあるが、工程・体制・環境・完了基準をまとめた**テスト計画書（全体）**がない。
- 不足: セキュリティテスト観点表、テストデータ設計、テスト計画書。
- 推奨: G-03 のセキュリティレビューと統合したテスト観点を `シナリオ戦略.md` に追加。テストデータ設計を `docs/test/` に追加。
- 根拠: `テスト戦略.md`「テナント分離」のみがセキュリティ関連、脆弱性観点なし。

### T-04【重要度: 低】受け入れテスト（UAT）観点が独立していない

- 現状: AC-XXX は単体/E2E に落ちるが、業務受け入れ（発注者観点での合否判定シナリオ）が独立成果物として整理されていない。
- 推奨: 必要に応じ `docs/test/受け入れ観点.md`（UC 単位の業務シナリオ × 合否基準）。
- 根拠: `シナリオ戦略.md` は E2E 自動化視点が中心。
