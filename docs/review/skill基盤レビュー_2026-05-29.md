# skill オーケストレーション基盤 レビュー結果

- 対象: `.claude/skills/` 配下の全 skill・テンプレート・共通スクリプト、`CLAUDE.md`、`docs/architecture/skill-orchestration.md`
- レビュー日: 2026-05-29
- 主眼: 工程網羅性・整合性 / skill 実装の品質
- レビュアー: Claude（Cowork）

## 凡例（重大度・略号）

| 略号 | 正式名称 | 意味・対応方針 |
| --- | --- | --- |
| **BLOCK** | 致命的欠陥 | この基盤を運用する前に修正が必要。放置すると工程が動かない／結果が破綻する |
| **SUGGEST** | 改善推奨 | 動作はするが品質・保守性・再現性に明確なリスク。早期対応が望ましい |
| **NIT** | 軽微 | 体裁・整理レベル。時間があれば対応 |
| produce / review / fix | ループの3段 | 成果物生成 → レビュー → 修正。Pattern 4（Iterative Loop） |
| state machine | 状態機械 | `.skills-state/<phase>/state.json` を真実の源とする決定論層 |

本レビューで使う ID 体系（`SCR-XXX` `UC-XXX` `AC-XXX` 等）は `CLAUDE.md` の定義に従う。

## エグゼクティブサマリ

要件定義フェーズの作り込み（ガードレール、非機能要件の要求値テンプレート、文書間整合チェック、レビュー観点の網羅）は完成度が高く、本基盤の最大の強みです。一方で、**フェーズをまたぐ整合性に複数の致命的な綻び**があります。とくに次の3点は運用前の修正を強く推奨します。

1. `implement-loop` が呼ぶ slash command 名が実 skill 名と一致しておらず、**実装フェーズのループが起動しない**（BLOCK）。
2. アーキテクチャ設計書は「Agent Teams は使用しない／11 agent は非推奨スタブ化」と宣言しているのに、`implement-from-issue` と `java-todo-team-bootstrap` は **agent team 前提**で書かれており正面衝突している（BLOCK）。
3. 「人手レビュー採択」ゲートが各 skill 冒頭の自己申告に依存しており、**機械的に強制する仕組みがない**（SUGGEST だが影響大）。

検出した指摘は BLOCK 4 件 / SUGGEST 12 件 / NIT 3 件です。以下、全体横断 → 各工程の順で示します。

---

## 1. 全体横断（フェーズをまたぐ整合性・基盤実装）

### 1-1. BLOCK — `implement-loop` の sub-skill 呼び出し名が実 skill 名と不一致

`implement-loop/SKILL.md` は review/fix 段で次を呼びます。

- `/review-implement`
- `/fix-implement`

しかし実在する skill 名（frontmatter `name:`）は **`review-implementation` / `fix-implementation`** です。slash command は skill 名と一致する必要があるため、現状では implement フェーズのループは review 段で解決に失敗します。`requirements-loop`（`/review-requirements` `/fix-requirements`）と `design-loop`（`/review-design` `/fix-design`）は正しく一致しているため、**implement だけが壊れています**。

> 推奨修正: `implement-loop/SKILL.md` の呼び出しを `/review-implementation` `/fix-implementation` に統一する。あわせて3ループで「loop が呼ぶ名 = 実 skill 名」を機械チェックする小スクリプト（grep ベース）を `_common/scripts/` に追加するとリグレッションを防げる。

### 1-2. BLOCK — アーキテクチャ設計書と実装系 skill が Agent Teams の扱いで矛盾

`docs/architecture/skill-orchestration.md` は次を明記しています。

- §1「Agent Teams は使用しない（experimental かつ並列実行は Pattern 2 で代替可能）」
- §8「11 個の agent はすべて skill 群に責務を移管し、**非推奨スタブ化**する」

ところが実装フェーズの中核 skill は agent team を前提に書かれています。

- `implement-from-issue/SKILL.md` 手順4・5: `springboot-backend-implementer` `react-frontend-implementer` `db-schema-implementer` `unit-test-engineer` `static-analysis-engineer` `e2e-test-engineer` `failure-investigator` を「teammate として起動」する。
- `java-todo-team-bootstrap/SKILL.md`: そもそも agent team 組成専用 skill として全体が存在する。

「設計書に従えば agent team は使わない」「実装 skill に従えば agent team を使う」のどちらが正なのか、運用者が判断できません。`CLAUDE.md` の9ステップフローは `implement-from-issue` を採用しているため、設計書 §1/§8 と実運用が食い違っています。

> 推奨修正: どちらの方針を採るか決定し、片方に寄せる。Agent Teams を使わないなら implement-from-issue の手順4・5を「単一セッション内の逐次実装＋Pattern 2 並列品質ゲート」に書き換え、`java-todo-team-bootstrap` を削除またはアーカイブ。使うなら設計書 §1/§8 を改訂する。

### 1-3. BLOCK — テストフェーズがループ化されておらず、独立 skill がフローから孤立している

`CLAUDE.md` の9ステップフローと設計書 §8 では、UT・静的解析・E2E は `implement-from-issue` 内の「品質ゲート（Pattern 2 並列）」に吸収する設計です。しかし次の skill が独立して残っており、9ステップフローのどこからも呼ばれていません。

- `unit-test-from-design` / `e2e-from-design` / `coverage-to-100` / `static-analysis-remediation`
- `implement-from-design`（`implement-from-issue` と責務が重複。Issue 起票を飛ばして設計から直接実装する旧経路）

これらは「オーファン skill（フローに接続されていない skill）」です。実装フェーズに produce-review-fix のループはありますが、**テスト成果物（`docs/test/`）には produce-review-fix のガードがありません**。結果として、テストの十分性は `review-implementation` の `coverage` 観点に一元依存し、テスト設計そのもののレビュー工程が欠落しています。

> 推奨修正: (a) オーファン skill を「実装ループから補助的に呼ばれる部品」と明示する（呼び出し元を SKILL.md に記載）か、不要なら削除。(b) `implement-from-design` は `implement-from-issue` と統合方針を決める。(c) テスト戦略・テストマトリクスのレビューを `review-implementation` の観点に明示追加する。

### 1-4. SUGGEST — 「人手レビュー採択」ゲートが機械的に強制されていない

`CLAUDE.md` は「採択前は次工程に進まない」を繰り返し要求し、`design-from-requirements` `create-issues-from-design` `implement-from-issue` も冒頭で「採択済みであること」を確認するよう書かれています。しかしこの確認は **AI の自己申告**であり、採択状態を表す機械可読なマーカー（state ファイルやラベル）が存在しません。`record-review.sh` の `passed=true` は BLOCK==0 で自動的に立つだけで、「人手が採択した」事実とは無関係です。

> 推奨修正: `.skills-state/<phase>/approved.json`（採択者・日時・対象コミット）のようなマーカーを導入し、後続 skill（design-loop / create-issues / implement-loop）の冒頭で **その存在を必須前提**にする。採択は人手で 1 コマンド実行する運用にすると、自己申告依存から脱却できる。

### 1-5. SUGGEST — escalation 判定ロジックが2スクリプトに分散し off-by-one リスクがある

終了・エスカレーション判定が `record-review.sh` と `advance-state.sh` の双方に分散しています。

- `record-review.sh`: `if s["iteration"] >= s["max_iterations"]` で escalate
- `advance-state.sh`: `if s["iteration"] > s["max_iterations"] and next_stage in (review, fix)` で escalate

境界条件（`>=` と `>`）が異なるため、`max_iterations` 到達時にどちらの経路を通るかで挙動がぶれます。判定が2箇所にあること自体が、片方だけ直して片方が取り残されるリグレッション源です。

> 推奨修正: 「BLOCK 残存かつ上限到達なら escalate」の判定を `record-review.sh` 1 箇所に集約し、`advance-state.sh` からは重複判定を外す（単純な stage 遷移と iteration++ のみに限定）。

### 1-6. SUGGEST — `record-review.sh` が history に追記せず、監査ログが設計と乖離している

設計書 §4 の state スキーマ例と §9 のアンチパターン回避は「各 stage 完了タイムスタンプを history に記録」「review stage には block 件数を残す」ことを前提にしています。しかし `record-review.sh` は `review_counts` と `stage` を更新するだけで **`history` に追記しません**。history への追記は `advance-state.sh` だけが行うため、review 完了イベントと BLOCK 件数が監査ログに残りません。

実際の `.skills-state/design/state.json` を見ると、history のタイムスタンプが非単調（`review` が `06:00:00`、その後の `fix` が `06:10:00`、さらに次の `review` が `05:45:50` と逆行）で、`done` への遷移も history に現れていません。これは history 記録が現状信頼できないことの実証です。

> 推奨修正: `record-review.sh` でも `history` に `{iteration, stage:"review", block:<n>, completed_at}` を追記する。タイムスタンプは UTC で単調になるよう、各スクリプトが必ず現在時刻を採るようにする（手編集された state を疑う）。

### 1-7. SUGGEST — state に実行環境依存の絶対パスが混入している

`.skills-state/design/state.json` の `last_review_path` が `/workspace/.skills-state/design/round-3-review.json`、`requirements` の `extra_args` が `/workspace/docs/requirements/requirement_matching.md` と、devcontainer 固有の絶対パス（`/workspace`）で記録されています。スクリプトは相対パス前提（`STATE_FILE=".skills-state/..."`）のため、別環境で state を引き継ぐと `last_review_path` の解決に失敗します。

> 推奨修正: state に保存するパスはリポジトリルートからの相対パスに正規化する。`fix-*` skill が `last_review_path` を Read する際も相対前提にそろえる。

### 1-8. SUGGEST — produce/review/fix sub-skill の起動制御が曖昧

`*-loop` と補助 skill は `disable-model-invocation: true` を持ちますが、produce（`requirements-from-input` 等）・review・fix は持ちません。とくに `requirements-guardrails` は description が非常に広く（「要件を整理して」等で発火）、常時オン気味です。ループからのみ呼ぶ意図の skill がモデル判断で誤起動する余地があります。一方で `CLAUDE.md` は produce skill を直接呼ぶ運用（`/requirements-from-input`）も想定しており、「ループ専用」か「単独起動可」かの意図が skill ごとに二重になっています。

> 推奨修正: 各 skill の冒頭に「単独起動可／ループ専用」を1行で明示。ループ専用にしたい review/fix は `disable-model-invocation: true` を付け、SlashCommand 経由に限定する。

### 1-9. NIT — 不要なテスト残骸ファイル

`.claude/skills/ui-brief-from-design/test_write.txt`（0 バイト）が混入しています。書き込みテストの残骸と思われます。削除推奨。

## 2. 要件定義フェーズ

`requirements-loop` / `requirements-from-input` / `review-requirements` / `fix-requirements` / `requirements-guardrails`（+ references 3 本）/ `requirements-template.md`

### 良い点（維持すべき強み）

- ガードレール（カテゴリ A〜D の MUST NOT、非機能要件の「方針→要求値」変換テンプレート、文書間整合チェック）が具体的で、AI が陥りやすい欠陥を的確に封じている。
- レビュー観点が網羅的（completeness / traceability / usecase / activity / data_model / external_interface / migration / security_baseline / open_question_closure / exception / status-drift / impl-leak 等）。
- 「未確定は本文に断定せず `[要確認]` 形式 + オープン課題転記」の運用が一貫している。

### 2-1. SUGGEST — review の観点数に対して fix 側のカテゴリ別対応指針が粗い

`review-requirements` は30近いカテゴリを定義しますが、`fix-requirements` の手順は「同一ファイル×同一カテゴリをまとめて編集」「BLOCK は必修・SUGGEST は対応」程度で、カテゴリごとの修正方針が対応づいていません。`fix-implementation` がカテゴリ別（quality_gate / coverage / design_mismatch …）に修正手順を持つのと非対称です。レビューの解像度が高いぶん、修正側の指針が薄いと反映品質がぶれます。

> 推奨修正: `fix-requirements` に主要カテゴリ（traceability / status-drift / impl-leak / open_question_closure 等）の修正パターンを数行ずつ追記する。

### 2-2. SUGGEST — 汎用テンプレートに特定ドメイン語が混入している

`CLAUDE.md` は「汎用 Web アプリ（React/Spring Boot）」基盤を謳いますが、`requirements-guardrails` のカテゴリ B 例と `requirements-from-input` 指示18は「セット応募」「荷主」「運送開始・完了報告」「合意フェーズ中に他社が先に成約」「アカウント登録（法人重複判定）」など、運送マッチング案件固有の語に強く依存しています。別ドメインで再利用するとこれらが誤誘導になります。

> 推奨修正: ドメイン固有例は references 配下の「実例集」に隔離し、SKILL.md 本文は抽象パターン（「競合する同時操作」「中間状態の表示方針」等）に置き換える。指示18のような案件固有の必須フローは、プロジェクト個別の追加指示ファイルに分離する。

### 2-3. NIT — 状態ファイル上の要件フェーズは未完（iteration=2, stage=fix）

`.skills-state/requirements/state.json` は BLOCK 3 件残・`passed=false` で停止しています。レビュー対象の事実確認としてのみ記載（skill の不具合ではなく運用途中の状態）。

## 3. 設計フェーズ

`design-loop` / `design-from-requirements` / `review-design` / `fix-design` / `design-spec-template.md`

### 良い点

- API（OpenAPI 3.1・リソース単位）/ DB（全体 ER + テーブル別部分 ER）/ 画面 / シーケンスの粒度と命名規約が明確。
- `review-design` の traceability 観点が要件 ID（SCR/UC/ACT/BR/AC）への逆参照を要求しており、要件→設計の追跡性を担保。
- `fix-design` に「API YAML 変更時は `_common.yaml` の `$ref` 波及確認」「DB 変更時は全体 ER と部分 ER の両更新」など整合チェックが具体的。

### 3-1. SUGGEST — シーケンス図のフロントエンド↔API↔DB粒度が要件側トリガと結びついていない

`design-from-requirements` 手順4.5はシーケンスに SCR/UC/ACT/API/AC の引用を求めますが、`review-design` の `sequence` BLOCK 観点は「SCR-XXX・UC-XXX・API operationId のいずれかが1件も引用されていない」と緩く、ACT（業務アクティビティ）との突合が SUGGEST 止まりです。要件フェーズで ACT を重視している割に、設計シーケンスとの紐付け検証が弱くなっています。

> 推奨修正: 分岐を持つ ACT に対応するシーケンスが存在するか（網羅性）を `review-design` の completeness BLOCK に1行追加する。

### 3-2. SUGGEST — 非機能要件（性能・可用性）が設計レビュー観点にほぼ反映されていない

要件フェーズは性能・可用性・バックアップ・障害通知を要求値で確定させますが、`review-design` の観点は performance（N+1・インデックス）程度で、要件で確定した数値（例: 一覧3秒/同時50ユーザー、RTO 4時間）が設計に落ちているかの突合がありません。非機能の traceability が要件→設計で途切れます。

> 推奨修正: `review-design` に「非機能要件の要求値が設計（DB インデックス方針・キャッシュ・バッチ設計など）に反映されているか」の観点を追加。

## 4. UI ブリーフ / Issue 起票フェーズ

`ui-brief-from-design` / `create-issues-from-design`

### 良い点

- 「共通ブリーフ→画面別ブリーフ（差分のみ）」の2層構造と Claude Design 投入順序の固定は、実証ベースで合理的。
- `create-issues-from-design` が handoff README の `scr-id → prototype 関数`マッピングを解析し、画面 Issue に prototype 参照・トークン参照・「モックを本番にコピーしない」注意を埋め込む設計が丁寧。

### 4-1. SUGGEST — UI フェーズに review/fix ループがなく、整合の Source of Truth が無検証

`ui-brief-from-design` 自身が「フィードバックループ（review/fix）は未整備」と明記しています。さらに `create-issues-from-design` は handoff の README マッピング表を Source of Truth として信頼しますが、**この表が設計書の画面一覧（SCR-XXX）と一致しているかを検証する工程がありません**。人手 Export の README が古い／画面 ID 欠落の場合、画面 Issue に誤った prototype 参照が埋まります。

> 推奨修正: 軽量な `review-ui-handoff`（README のマッピング表 ⇔ `docs/design/screens/` の SCR-XXX 突合のみ）を追加し、`create-issues-from-design` の前提チェックに組み込む。フルループでなく整合チェック1本でも効果が大きい。

### 4-2. SUGGEST — Issue 起票に冪等性・再実行ガードがない

`create-issues-from-design` はタイトル近似検索で重複検出しますが、ヒット時は「ユーザーに確認」と人手依存です。設計が更新されて再起票する運用での冪等性（既存 Issue 更新 vs 新規）が定義されていません。

> 推奨修正: 「SCR-XXX をタイトルに含める規約」を活かし、`[SCR-XXX]` 一致で既存 Issue を検出したら新規作成せず更新コメントに切り替える分岐を明記する。

## 5. 実装 / テスト / 共通基盤フェーズ

`implement-loop` / `implement-from-issue` / `review-implementation` / `fix-implementation` / `unit-test-from-design` / `e2e-from-design` / `coverage-to-100` / `static-analysis-remediation` / `java-todo-team-bootstrap` / `_common/scripts/*`

> 本フェーズの最重要事項は §1-1（slash command 名不一致 = BLOCK）、§1-2（Agent Teams 矛盾 = BLOCK）、§1-3（テストループ欠如 = BLOCK）。ここでは個別の追加点を示す。

### 良い点

- `review-implementation` の BLOCK 観点（quality_gate / coverage<80% / design_mismatch / security / architecture / git 直 push 禁止）が CLAUDE.md の開発ルールと整合。
- `fix-implementation` がカテゴリ別修正手順 + 「`main`/`develop` 直 push 禁止」「`.github/workflows` 編集禁止」「`git add -A` 禁止」を明記し、安全側に倒している。
- `check-truncation.sh` が差分ファイルにも適用され、コード（.java/.ts）の UTF-8 破損も拾う設計。

### 5-1. SUGGEST — テスト成果物（`docs/test/`）に truncation チェックと ID 体系がない

`review-requirements`/`review-design` は `check-truncation.sh` を `docs/requirements/` `docs/design/` に回しますが、`docs/test/`（単体テストマトリクス・E2E シナリオ）は対象外です。また `CLAUDE.md` の ID 体系は SCR/UC/ACT/ENT/ST/EXT/MIG/SEQ/BR/AC/Q-* を定義する一方、**テストケース ID（例 TC-XXX / E2E-XXX）の採番規約がありません**。テンプレートでは `E2E-01` 等を例示しているのに、ID 規約・凡例ルールの対象外です。

> 推奨修正: テストケース ID 規約を `CLAUDE.md` の ID 体系に追加し、AC-XXX ↔ テスト ID の対応をマトリクスで必須化。`docs/test/` も truncation チェックの対象に含める。

### 5-2. SUGGEST — テンプレートのボリュームが工程間で極端に不均衡

`requirements-template.md`（725行）・`design-spec-template.md`（718行）に対し、`unit-test-matrix-template.md`（12行）・`e2e-scenario-template.md`（13行）は骨だけです。上流の作り込みに対しテスト工程のテンプレートが薄く、AC との対応や境界値の体系化が現場任せになります。

> 推奨修正: テストテンプレートに「AC-XXX 列の必須化」「正常/異常/境界/権限の区分必須」「対応する SCR-XXX・API operationId 列」を追加して上流と粒度をそろえる。

### 5-3. SUGGEST — 品質ゲートの「実行済み」証跡が口頭依存

`review-implementation` は「品質ゲートが実行されていなければ BLOCK」としますが、判定材料は `build/`/`target/`/`coverage/`/`playwright-report/` の存在確認に依存し、`implement-from-issue` 側がレポートを所定パスに必ず出力する保証（コマンド固定）がありません。エージェント任せだとレポート未生成でも「緑」と報告されうる構造です。

> 推奨修正: `implement-from-issue` の品質ゲートに「カバレッジ/解析/E2E の出力パスを固定し、`review-implementation` がそのパスの新しさ（タイムスタンプ）を確認する」手順を明記する。

### 5-4. NIT — `coverage-to-100`（100%目標）と CLAUDE.md（カバレッジ80%基準）の温度差

`review-implementation` の BLOCK は「<80%」、`coverage-to-100` は「100% に近づける」で、目標水準の表現が混在しています。実害は小さいですが、運用者が「目標は80か100か」を迷います。

> 推奨修正: 「合格ライン80% / 努力目標として coverage-to-100 を任意適用」と関係を1行で明記。
