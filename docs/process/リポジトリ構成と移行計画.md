# リポジトリ構成と移行計画

> マルチリポジトリ構成（アンブレラ + 6 リポジトリ）の決定事項と、現状（単一 `claude-poc`）からの移行手順を記録する。
>
> ⚠️ 本書は計画・参考。正典は各リポジトリの `CLAUDE.md` / `rules/`。実ファイルの移動・パス再設定は**子リポジトリ作成後・ルール安定後**に一括で行う（それまでは現状維持）。

## 1. 決定事項（チーム合意）

- **6 リポジトリ構成**。コードと、それを律するルールは同じリポジトリに同梱する（ルールはコードと一緒に旅する）。
- **親（AIルール用）をアンブレラ**とし、その中の `repos/` フォルダに子リポジトリを配置する。
- 子のネストは **素クローン + 親側 `.gitignore`**（submodule は使わない。再現性が必要になった時点で再検討）。
- **GitHub Projects v2** で 6 リポジトリを 1 ボードに集約。Issue は各リポジトリに分散し、`Closes #N` の自動クローズを活かす（→ `06-issue-management.md` §17）。
- **Claude / devcontainer は親（アンブレラ）から動かす**。親の `.claude`（deny・`protect-canon` フック）が全子に効く（フックはネストした `rules/` も保護対象）。
- **技術スタックの確定値は事前にルールへ追記しない**（ルールは原本に近い形を維持）。要件定義・設計フェーズのスキル実行時に、未確定項目を人間へ確認し、確定した値をその時点で各リポジトリの rules に追記する（CLAUDE.md「未指定なら中断して人間に指定を求める」のハードゲートで担保）。

### リポジトリ一覧

| リポジトリ | 役割 | 同梱するルール | Issue の主な中身 |
|---|---|---|---|
| **親：AIルール用**（アンブレラ） | `CLAUDE.md`・開発フロー/横断 AI ルール・skills（`.claude`）・`.devcontainer`・`repos/` | 横断 AI ルール（フロー・ID/命名規約・正典保護） | ルール/フロー/skill 変更・メタ |
| ドキュメント用（**docs**） | 要件定義・設計書（`docs/requirements`・`docs/design`） | 設計記述ルール（任意） | 要件/設計タスク・エピック |
| FE 用 | フロントエンド実装 | `frontend-*.md` | 画面（SCR）実装 |
| BE 用 | バックエンド実装 | `backend-*.md`（アーキ＋スタック） | API/DB 実装 |
| バッチ用 | バッチ実装 | バッチルール | バッチ実装 |
| E2E 用 | E2E（デプロイ後工程） | E2E ルール | E2E シナリオ実装 |

```
親（AIルール用） = 現 claude-poc を作り替え
├─ CLAUDE.md / .claude/ / .devcontainer/
├─ rules/                  ← 横断 AI ルールのみ残す（技術スタック/実装規約は各子へ移動）
├─ docs/process/ 等        ← 運用ドキュメント
└─ repos/                  ← .gitignore 対象。子を素クローン
   ├─ docs/     （ドキュメント用：要件定義+設計書）
   ├─ frontend/ （FE 用）   rules/frontend-*.md
   ├─ backend/  （BE 用）   rules/backend-*.md
   ├─ batch/    （バッチ用） rules/...
   └─ e2e/      （E2E 用）   rules/...
```

### 1.1 子リポジトリの自己完結性（GitHub Actions 前提）

Issue 起点の自動実行は**各子リポジトリの GitHub Actions** で行うため、CI の実行コンテキストは子リポジトリ単体のチェックアウトになる（親アンブレラは存在しない）。よって各子は Claude 実行に必要な一式を自己完結で持つ。

- `.claude/skills/`（その repo の実装・レビュー系スキル）
- `.claude/rules/`（その repo のルール。自動読み込み・`paths:` frontmatter でスコープ可）
- `CLAUDE.md`（その repo 向け指示）
- **`.claude/settings.json` + hooks（deny・protect-canon 相当）** — 親のガードレールは CI では効かないため子にも複製必須
- Secrets（`ANTHROPIC_API_KEY` 等）は Organization レベルの Actions Secrets で一元管理

### 1.2 採択ゲート：シェル承認を廃止し Issue ラベルゲートへ（決定）

- `approve-phase.sh` → `.skills-state/<phase>/approved.json` による**ローカル採択ゲートは廃止**する（CI から不可視で自動化の妨げ）。
- 置き換え: **採択後に人手で `status:ready` ラベルを付与**し、自動実行（workflow / ディスパッチ）は `status:ready` のみをトリガーにする。承認者・承認時刻は Issue タイムラインが証跡。
- ガード: `status:ready` の付与は人間のみ。skill には「自身で `status:ready` を付与しない」を明記（必要なら hook で `gh issue edit ... --add-label status:ready` をブロック）。
- 波及: CLAUDE.md の採択ゲート記述・`create-issues-from-design` / `implement-from-issue` の approved.json 前提を撤去（→ §2 ステップ 7）。

### 1.3 共有資産（ループ制御・共通スクリプト・共有スキル）の参照方式

子から親を**直接参照は CI では不可**（子単体チェックアウトのため）。シンボリックリンクはコミット可能だがリンク先が CI に存在せず**不成立**（Windows の symlink 制約もあり）。Git 的に子へコミットされている必要はなく、**CI 実行時にファイルが存在すればよい**。選択肢:

| 方式 | 概要 | 評価 |
|---|---|---|
| 親の追加チェックアウト | workflow で `actions/checkout` を2回（親→ `.ai-rules/` 等）+ `claude --add-dir` | **短期推奨**。最小変更・単一ソース維持 |
| プラグイン化 | 親 AIルール repo を plugin marketplace にして共有スキルを配布 | **長期推奨**。バージョン管理込みで最もきれい |
| submodule | 子が共通部分を submodule 参照（CI は `submodules: true`） | 動くが運用が重い |
| 各子へコピー | 共有物を複製 | ドリフト必至。非推奨 |

### 1.4 レビュー JSON の位置づけ（継続）

review skill の JSON 出力は**ループ制御の決定論性のため継続**する（BLOCK 件数の機械集計で done / fix / escalate を分岐、fix への構造化入力、round ごとの状態保存・検証）。GitHub 移行後は「機械用 JSON + 人間用 PR コメントサマリ + `review:*` ラベル」の両建てとする。

## 2. 移行ステップ（子リポジトリ作成後・ルール安定後に実施）

1. **子リポジトリと Project を作成**：docs / frontend / backend / batch / e2e を作成。GitHub Projects v2 を 1 つ作り 6 リポジトリを紐付け（gh）。トークンに `project` 権限を付与（`06-issue-management.md` §17.5）。
2. **親の整備**：`repos/` を作成し `.gitignore` に追加（embedded repo 警告回避のため必須）。`CLAUDE.md`・`.claude`・`.devcontainer`・skills は親に残す。
3. **ルール移動（① 単一ソースの再配置）**：親 `rules/` の `frontend-*.md`→FE、`backend-*.md`（アーキ＋スタック）→BE、バッチルール→batch、E2E ルール→e2e。各ルールの home は 1 か所のまま（二重管理しない）。親 `rules/` には横断 AI ルールのみ残す。
4. **CLAUDE.md 更新（①）**：「技術スタックの正典＝`rules/`」を「**各リポジトリの `rules/`**」へ書き換え。`protect-canon` フックは据え置き（`(^|/)rules/` でネストした子の `rules/` も保護、CLAUDE.md も保護）。
5. **設計書移動（② パス波及・影響大）**：`docs/requirements`・`docs/design` をドキュメントリポジトリ（docs）へ。アンブレラ内マウント配置（仮：`repos/docs/`）を確定し、skills が前提にする `docs/requirements/`・`docs/design/` のパス参照を**一括更新**する。
6. **Issue 運用（③ 仮）**：`06-issue-management.md` §17.2 の振り分け（E2E・設計書を追加済み）、`batch.md`・`e2e.md` テンプレ追加、各 repo へのラベル複製、gh 一本化。
7. **採択ゲートの置き換え（§1.2）**：`approve-phase.sh` / `approved.json` の仕組みを撤去し、CLAUDE.md の採択ゲート記述と `create-issues-from-design` / `implement-from-issue` の前提条件を `status:ready` ラベルゲートへ書き換える。
8. **子の自己完結化（§1.1）**：各子に `.claude/skills` / `.claude/rules` / `CLAUDE.md` / `.claude/settings.json` + hooks を配置。共有資産の参照方式（§1.3）を確定して workflow を整備する。

## 3. 未確定・要検討（open）

- **ドキュメントリポジトリのアンブレラ内パス**：仮 `repos/docs/`。確定後、skill パスを更新（②）。
- **移行着手タイミング**：ルールが流動中のため、安定後に一括実施を推奨。
- 各リポジトリの remote URL・命名規約（org/user、`<org>/fe` 等）。
- 子単体で Claude / CI を回す運用の要否（→ §1.1 により **CI は子単体で回す**方針に更新。ローカルは親アンブレラから）。
- 共有資産の参照方式の確定（§1.3。短期=親の追加チェックアウト / 長期=プラグイン化）。
